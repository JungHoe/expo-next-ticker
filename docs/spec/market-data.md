# 시세 데이터

- 상태: 확정
- 관련 이슈: #9, #10, #11, #12 (spec 작성 #6)

## 1. 목적
웹과 앱이 같은 시각에 같은 시뮬레이션 시세를 받는다. 데이터는 실제 네트워크를 거치게 해서 로딩, 오류, 재시도, 오프라인 상태를 연출 없이 다룰 수 있게 한다.

## 2. 화면
없음. 관심 종목(`watchlist.md`)과 종목 상세(`stock-detail.md`)가 이 계층을 쓴다.

## 3. 데이터
- 위치: `packages/market`(플랫폼 중립). 시세 API만 `apps/web`의 Route Handler에 둔다
- 출처: 시뮬레이션. 화면에는 항상 "시뮬레이션 시세"라고 표시한다(design.md §7)

### 종목 목록 (고정)
`AAPL` Apple, `MSFT` Microsoft, `NVDA` NVIDIA, `AMZN` Amazon, `GOOGL` Alphabet, `META` Meta Platforms, `TSLA` Tesla, `AVGO` Broadcom, `JPM` JPMorgan Chase, `V` Visa. 종목마다 시뮬레이션 기준가(예: 100~600 사이 상수)를 둔다. 목록에 없는 티커는 404다.

### 생성기
`priceAt(ticker, time)` 하나로 모든 값을 만든다.
- **결정적**: 같은 종목, 같은 초면 어디서 계산해도 같은 값이다. 1초 단위로 값이 바뀐다
- **O(1)**: 과거부터 차례로 쌓아 계산하지 않는다. 한 달 전 값도 바로 계산할 수 있어야 차트 이력을 만들 수 있다
- **그럴듯함**: 1시간 차트에서 주기가 눈에 띄지 않고, 한 달 동안 기준가의 ±25% 안에 머문다
- **24시간 움직인다**: 실제 장 시간 개념이 없다. 장이 닫힌 시간에도 시연할 수 있다
- 방식(사인파 합성, 해시 노이즈 등)은 빌더가 정한다

### 기준 시각과 파생 값
- **기준가**: 오늘 0시(KST)의 가격. 등락과 등락률은 기준가 대비다. 화면 문구는 "오늘 0시 대비"
- **고가·저가**: 오늘 0시부터 지금까지 1분 간격 값과 현재가 중 최고·최저(현재가를 넣지 않으면 현재가가 고가보다 높게 보이는 순간이 생긴다, #9)
- 실제 시장의 "전일 종가", "시가"는 시뮬레이션에서 의미가 없으므로 쓰지 않는다

### 차트 이력
| 기간 | 범위 | 간격 | 점 개수 |
|---|---|---|---|
| 1시간 | 지금부터 1시간 전 | 30초 | 121 |
| 1일 | 24시간 전 | 10분 | 145 |
| 1주 | 7일 전 | 1시간 | 169 |
| 1개월 | 30일 전 | 6시간 | 121 |

### 시세 API (`apps/web`)
- `GET /api/quotes?tickers=AAPL,MSFT` → 종목별 `{ ticker, name, price, change, changePct, base, high, low, asOf }`. 생략하면 전체 목록
- `GET /api/quotes/{ticker}/history?range=1h|1d|1w|1m` → `{ ticker, range, points: [{ t, p }] }`
- 없는 티커는 404, 잘못된 `range`는 400. 오류 본문도 정해진 형태(`{ error: { code, message } }`)다
- 시세 응답은 CDN에 1초 캐시한다(`s-maxage=1, stale-while-revalidate=1`). 응답 시점부터 세므로 최대 약 2초 지난 값이 나갈 수 있다. 오류 응답은 입력만으로 정해지므로 60초 캐시한다
- `tickers`는 쉼표로 묶거나 반복(`?tickers=AAPL&tickers=MSFT`)해도 된다. 티커는 대문자만 받는다(`aapl`은 404)
- 인증·쿠키 없는 공개 GET이라 CORS를 연다(`Access-Control-Allow-Origin: *`). Expo 웹 미리보기가 다른 출처에서 부른다
- 고가·저가는 요청마다 0시부터 다시 계산한다. 가장 무거운 23:59에도 10종목 0.87ms/요청이라, 1초 폴링을 30일 내내 켜도 CPU 약 37분으로 Hobby 한도(Active CPU 월 4시간) 안이다. 메모는 상태를 가진 코드를 늘리므로 두지 않는다(#11에서 측정)

### 스키마와 훅
- Zod 스키마를 `packages/market`에 두고, 서버는 응답을 만들 때, 클라이언트는 받을 때 같은 스키마로 검증한다
- 진입점: 서버에서도 쓰는 코드(스키마·생성기·API 함수·클라이언트)는 `@ticker/market`, 훅과 조회 설정은 `@ticker/market/react`. 서버 코드(Route Handler)에 React 훅이 딸려 가지 않게 나눈다(#12)
- TanStack Query 훅: `useQuotes()`(전체 목록, 화면에서 하나만 쓴다), `useQuote(ticker)`(`useQuotes()`의 결과에서 고른다. 요청을 따로 보내지 않는다), `useHistory(ticker, range)`. API 주소는 설정으로 주입한다(웹은 같은 출처, 앱은 `EXPO_PUBLIC_API_BASE_URL`, 기본값은 배포 주소)

### 차트 좌표 계산
`packages/chart`에 순수 함수로 둔다(시세와 무관한 계산이라 별도 패키지, #10). 점 배열, 그릴 영역 크기, 선택적으로 기준값을 받아 SVG 경로 문자열, y축 눈금 3~5개, x축 시각 라벨, 기준값의 y 좌표(범위 밖이면 `null`)를 돌려준다. y 범위는 데이터의 최솟값·최댓값으로 정한다. 그리는 일은 웹(`<svg>`)과 앱(`react-native-svg`)이 각자 한다.

## 4. 동작 규칙
| 상태 | 웹 | 앱 |
|---|---|---|
| 갱신 주기 | 시세 1초 폴링. 탭이 보이지 않으면 멈춘다 | 시세 1초 폴링. 앱이 백그라운드면 멈춘다(`AppState`) |
| 이력 | 기간을 바꿀 때 받는다. 1시간 차트는 폴링한 시세로 마지막 점을 이어 붙인다 | 같음 |
| 오류·재연결 | 시세는 재시도 없이 다음 폴링(1초 뒤)이 곧 재시도다. 이력은 확정 오류(4xx·형태 오류)는 재시도하지 않고 일시 오류만 1초 간격 2번. 실패해도 마지막 값은 남는다. 화면 표시는 각 화면 spec | 같음. 오프라인 감지는 `@react-native-community/netinfo`(Expo Go 포함). 오프라인이면 TanStack이 요청을 오류가 아니라 일시정지(`fetchStatus: "paused"`)로 둔다 |
| 장 마감 시간 | 해당 없음(24시간 시뮬레이션) | 같음 |

## 5. 수용 기준
앱 화면은 Expo 웹 미리보기(`expo start --web`)로 배치·색·차트를 확인한다. **(기기)** 표시 기준은 브라우저로 판정할 수 없는 네이티브 동작이라, 안드로이드 기기를 쓸 수 있을 때 #4와 함께 몰아서 확인한다(지원자 결정).

- [ ] 단위 테스트: `priceAt`이 같은 입력에 같은 값을 내고, 1초 안에서는 값이 같다
- [ ] 단위 테스트: 모든 종목이 30일 동안 기준가 ±25% 안에 있다(1분 간격 표본)
- [ ] 단위 테스트: 기준가·고가·저가·등락률 계산이 정의(§3)와 맞다
- [ ] `GET /api/quotes`, `GET /api/quotes/{ticker}/history`가 §3의 형태로 응답하고, 응답이 Zod 스키마를 통과한다
- [ ] 없는 티커 404, 잘못된 기간 400을 정해진 오류 형태로 돌려준다
- [ ] 같은 시각에 웹과 앱이 같은 가격을 받는다(두 클라이언트 모두 같은 API를 쓰므로 API 응답으로 확인)
- [ ] `useQuotes`, `useHistory`가 `packages/market`에 있고, React Native·DOM API를 import하지 않는다
- [ ] 차트 좌표 함수의 단위 테스트: 경로가 영역 안에 있고, 눈금이 3~5개이며, 최솟값·최댓값이 영역 경계에 맞고, 범위 밖 기준값은 `null`이다
- [ ] 웹 탭이 보이지 않을 때 폴링이 멈춘다
- [ ] **(기기)** 앱이 백그라운드로 가면 폴링이 멈추고, 돌아오면 다시 시작한다
- [ ] 목록과 상세가 함께 보이는 화면에서도 시세 요청은 초당 1회다(앱 스택에 목록이 남아 있어도 같다)

## 7. 결정 기록
- **API + 폴링**(지원자 선택): 기기에서 직접 계산하는 방식과 비교했다. 네트워크를 거쳐야 로딩·오류·재시도·오프라인 상태가 실제로 생기고, 그 상태들의 UX를 설계할 수 있다. 대가는 앱이 배포된 웹 API에 의존한다는 점이다
- **한계: 캐시 우회**(설계자 판단): CDN 캐시 키에 쿼리 문자열이 들어가므로 의미 없는 파라미터를 붙이면 매번 함수가 실행된다. 막으려면 Vercel Firewall·rate limit이 필요하고, 이 과제 범위 밖이다(#11 리뷰)
- **SSE를 쓰지 않음**(설계자 판단): Vercel 서버리스 함수는 오래 연결을 유지하기 어렵고, RN에는 `EventSource`가 없어 폴리필이 필요하다. 1초 폴링으로 충분하다
- **결정적 생성기**(design.md): 같은 시각에 웹과 앱이 같은 가격을 보여야 한다. 서버에서 계산하므로 기기 시계가 달라도 값이 같다
- **"전일 종가" 대신 "오늘 0시 기준가"**(설계자 판단): 24시간 시뮬레이션에는 장 마감이 없다. 실제 시장 용어를 흉내 내지 않는다
- **요청 수를 줄이는 설계**(설계자 판단): Vercel Hobby 요금제의 함수 호출은 월 100만 회다. 1초 폴링 화면 하나가 하루 8만 6천 회를 부르므로, 목록·상세가 요청 하나를 같이 쓰고 CDN 1초 캐시를 둔다. 계산 메모는 측정해 보니 필요 없었다(§3). 한도를 넘어 웹이 멈추면 같은 API를 쓰는 앱도 함께 멈춘다
- **고빈도 갱신 성능 측정**: 폴링 주기와 별개로, 생성기를 직접 빠르게 돌려 차트에 넣는 방식으로 측정한다(성능 이슈에서 정한다)
